# Adaptive Energy-Aware Clipped Double Deep Q-Learning for Multi-Objective Cloud Task Scheduling (AE-CDDQL)

A complete PyTorch implementation, experimental evaluation framework, and ablation study based on the baseline research paper:
> **"Task Scheduling in Cloud Using Deep Reinforcement Learning"**  
> Shashank Swarup, Elhadi M. Shakshuki, Ansar Yasar  
> *Procedia Computer Science*, Vol. 184, pp. 42–51, 2021. [DOI: 10.1016/j.procs.2021.03.016](https://doi.org/10.1016/j.procs.2021.03.016)

---

## 1. Executive Summary & Project Overview

Cloud datacenters process massive volumes of heterogeneous, latency-sensitive tasks generated by IoT devices and web applications. Traditional heuristics (such as Random, Round Robin, and Greedy Min-Min) either cause severe queue congestion, waste energy on underutilized nodes, or ignore long-term system dynamics.

The baseline paper proposed a **Clipped Double Deep Q-Learning (CDDQL)** scheduler to allocate tasks to Virtual Machines (VMs). While CDDQL reduced TD error overestimation compared to standard DQN, the baseline paper had three key limitations:
1. **Fixed Exploration ($\epsilon = 0.5$):** The agent continually takes 50% random actions throughout execution, destroying scheduling efficiency at inference time or failing to exploit converged policies.
2. **Limited 3D State Representation:** The state only observes `(CPU, Memory, Storage)` of the current task, blind to VM queue backlogs and power profiles.
3. **Unidimensional Rank-Only Reward:** The baseline assigned fixed rewards ($+2, +1, -1, -2$) based purely on VM speed ranking, incentivizing the agent to greedily route all tasks to the single fastest VM, creating massive queue waiting delays ($>59$ seconds) and leaving the rest of the datacenter idle.

### The Proposed AE-CDDQL Solution
To overcome these limitations, **AE-CDDQL** introduces **3 targeted modifications**:
1. **Adaptive $\epsilon$-Greedy Policy:** Replaces the rigid $\epsilon = 0.5$ with an exponential exploration decay schedule that transitions smoothly from global exploration ($\epsilon_{start} = 1.0$) to high-precision exploitation ($\epsilon_{end} = 0.02$).
2. **5D Energy-Aware State Space:** Expands the state vector to `(CPU, Memory, Storage, Workload, Energy)`, providing real-time visibility into cumulative datacenter workload and energy footprints.
3. **Multi-Objective Reward Function:** Directly penalizes Execution Time, Waiting Time, and Energy Consumption simultaneously:
   $$R_{MO} = - \left( \alpha \frac{T_{exec}}{T_{exec}^{max}} + \beta \frac{T_{wait}}{T_{wait}^{max}} + \gamma \frac{E_{task}}{E^{max}} \right)$$

## 2. Theoretical Architecture & Mathematical Formulations

### 2.1 Baseline CDDQL Formulation
In CDDQL, two neural network approximators ($Q_1$ and $Q_2$) with parameters $\theta_1$ and $\theta_2$ are maintained alongside their target networks ($Q_1'$ and $Q_2'$ with parameters $\theta_1'$ and $\theta_2'$).

The Bellman target in CDDQL (Equation 3 in the baseline paper) is computed by taking the minimum target estimate:
$$y = r + \gamma \min_{i \in \{1, 2\}} Q_i'\left(s', \arg\max_{a'} Q_1(s', a'; \theta_1); \theta_i'\right)$$

Target networks are updated using Polyak soft updates (Equation 4 in the paper):
$$\theta_i' \leftarrow \tau \theta_i + (1 - \tau)\theta_i', \quad \text{with } \tau = 0.01$$

The loss function for both networks is the Mean Squared Temporal Difference Error:
$$L(\theta_i) = \mathbb{E}_{(s, a, r, s') \sim \mathcal{D}} \left[ \left( Q_i(s, a; \theta_i) - y \right)^2 \right]$$

### 2.2 Neural Network Architecture
As specified in Section 4.1 of the baseline paper, each Q-network is implemented as a PyTorch sequential model containing:
- **Input Layer:** Matches state dimension (3 for baseline, 5 for AE-CDDQL)
- **Dense Layer 1:** 128 hidden units + ReLU activation
- **Dense Layer 2:** 128 hidden units + ReLU activation
- **Dense Layer 3:** 128 hidden units + ReLU activation
- **Dense Layer 4:** 128 hidden units + ReLU activation
- **Output Layer:** Linear projection to action space ($|\mathcal{A}| = 4$ VMs)
- **Optimizer:** Adam ($\alpha = 10^{-3}$)

## 3. The 3 Core Proposed Modifications

| Component | Baseline CDDQL (Paper) | Proposed AE-CDDQL | Impact |
| :--- | :--- | :--- | :--- |
| **1. Exploration Policy** | Fixed $\epsilon = 0.5$ | Adaptive Exponential Decay: $\epsilon(t) = \epsilon_{end} + (\epsilon_{start} - \epsilon_{end})e^{-\lambda t}$ | Eliminates random mistakes during deployment; stabilizes policy convergence. |
| **2. State Representation** | 3D: `(CPU, Memory, Storage)` | 5D: `(CPU, Memory, Storage, Workload, Energy)` | Gives RL agent visibility into VM queue backlog and cumulative datacenter power. |
| **3. Reward Function** | Discrete Speed Ranking: $+2, +1, -1, -2$ | Multi-Objective Penalty: $-(\alpha \widetilde{T}_{exec} + \beta \widetilde{T}_{wait} + \gamma \widetilde{E})$ | Balances execution speed against queue waiting congestion and energy consumption. |

## 4. Experimental Results & Verification

All experiments were executed on the standardized **Google Task Events** benchmark workload as described in Section 4.1 and Section 4.2 of the paper:
- **VM Configuration:** 4 Heterogeneous VMs with 500 MB RAM and 1000 MB Storage each.
  - VM 0 (Best/Fastest): 100 MB/s, $P_{idle}=80$W, $P_{run}=220$W, Cost=\$0.00008/s
  - VM 1 (2nd-Best): 75 MB/s, $P_{idle}=60$W, $P_{run}=175$W, Cost=\$0.00006/s
  - VM 2 (3rd-Best): 50 MB/s, $P_{idle}=45$W, $P_{run}=130$W, Cost=\$0.00004/s
  - VM 3 (Slowest): 25 MB/s, $P_{idle}=30$W, $P_{run}=90$W, Cost=\$0.00002/s
- **Workload Benchmark:** 5 batches of 9 tasks each (45 tasks total, matching Figure 2 of the paper).
  - Tasks 1–4: 431 MB
  - Tasks 5–6: 213 MB
  - Tasks 7–8: 228 MB
  - Task 9: 248 MB

### 4.1 Comparative Evaluation Across Schedulers
*(Directly extracted from `results/csv/multi_batch_evaluation.csv`)*

| Scheduler | Makespan (s) | Avg Exec Time (s) | Avg Wait Time (s) | Total Energy (J) | Cost ($) | Avg Utilization (%) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **Random** | 100.52 | 5.64 | 17.21 | 36,613.33 | 0.01166 | 63.11% |
| **Round Robin** | 142.02 | 6.55 | 23.14 | 38,303.80 | 0.01152 | 51.91% |
| **Greedy EFT (Min-Min)**| 59.17 | 4.99 | 15.40 | 35,096.97 | 0.01156 | 94.88% |
| **Min Workload** | 141.22 | 6.56 | 23.27 | 38,304.20 | 0.01152 | 52.22% |
| **QLS (Tabular)** | 81.31 | 4.99 | 23.29 | 35,989.00 | 0.01234 | 69.04% |
| **CDDQL (Baseline Paper)**| 142.70 | **3.17** | 59.95 | 31,394.00 | **0.01142** | 25.00% |
| **AE-CDDQL (Proposed)** | **131.70** | 3.32 | **49.60** | 31,980.77 | 0.01173 | **28.34%** |

#### Key Insights:
1. **The Baseline CDDQL Trap:** Because the baseline reward is purely rank-based (+2 for VM 0), the baseline CDDQL agent routes every task to VM 0. While per-task execution time is low (3.17s), tasks queue up behind one another, blowing up **average waiting time to 59.95s** and leaving 75% of the cloud cluster idle (utilization = 25%).
2. **AE-CDDQL Optimization:** AE-CDDQL slashes average waiting time by **10.35 seconds (~17.3% reduction)** and cuts total makespan from 142.70s to 131.70s, while maintaining minimal energy footprint (~31.9 kJ) and improving VM cluster utilization.

### 4.2 Complete Ablation Study
*(Directly extracted from `results/csv/ablation_study.csv`)*

The 5 requested ablation variants were evaluated under identical conditions (same seed, 150 training episodes, 45-task test benchmark):

| Ablation Variant | State Space | $\epsilon$ Policy | Reward Function | Makespan (s) | Avg Wait Time (s) | Total Energy (J) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **1. CDDQL (Baseline)** | 3D | Fixed (0.5) | Baseline Rank | 142.70 | 59.95 | 31,394.0 |
| **2. CDDQL + Adaptive $\epsilon$** | 3D | Adaptive | Baseline Rank | 142.70 | 59.95 | 31,394.0 |
| **3. CDDQL + Energy State** | 5D | Fixed (0.5) | Baseline Rank | 142.70 | 59.95 | 31,394.0 |
| **4. CDDQL + MO Reward** | 3D | Fixed (0.5) | Multi-Objective | 285.40 | 131.90 | 37,102.0 |
| **5. Full AE-CDDQL** | **5D** | **Adaptive** | **Multi-Objective** | **133.88** | **51.44** | **31,631.6** |

#### Ablation Analysis:
- In Variants 1–3, because the reward function rewards only VM speed, the agents converge to routing solely to VM 0 regardless of state or exploration.
- In Variant 4, adding the Multi-Objective reward with fixed $\epsilon=0.5$ causes erratic random actions at test time, resulting in poor scheduling.
- **In Variant 5 (Full AE-CDDQL), all three components synergize:** The 5D state provides the necessary queue backlog information, the MO reward provides the gradient signal penalizing delays and energy, and the adaptive $\epsilon$ decay allows the policy to converge cleanly and exploit optimal allocations, achieving the best overall performance.

## 6. How to Run the Project

### Prerequisites
- Python 3.10+ (tested on Python 3.13)
- PyTorch 2.0+ (CPU or CUDA)
- Standard scientific stack: NumPy, Pandas, Matplotlib, Seaborn

### Step 1: Install Dependencies
```bash
pip install -r requirements.txt
```

### Step 2: Run Unit Tests
Verify environment integrity, queuing math, and network updates:
```bash
python -m unittest discover tests
```

### Step 3: Run the Complete Master Experiment
Executes training, the full 5-variant ablation study, multi-scheduler evaluation, and plot generation:
```bash
python run_all_experiments.py
```
*(Runs in ~80-90 seconds on a standard laptop CPU).*

### Step 4: Individual Pipeline Commands (Optional)
To run stages independently:
- **Train Baseline CDDQL:**
  ```bash
  python -m experiments.train --model CDDQL-Baseline --episodes 150
  ```
- **Train Proposed AE-CDDQL:**
  ```bash
  python -m experiments.train --model AE-CDDQL --episodes 150
  ```
- **Run Ablation Study Only:**
  ```bash
  python -m experiments.run_ablation --episodes 150 --batches 5
  ```
- **Run Multi-Scheduler Evaluation Only:**
  ```bash
  python -m experiments.evaluate
  ```
- **Regenerate Plots Only:**
  ```bash
  python -m experiments.plot_results
  ```
